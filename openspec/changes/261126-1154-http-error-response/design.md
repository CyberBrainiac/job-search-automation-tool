# Design — 261126-1154 HTTP error response

The flow, the types and the examples are in [`docs/error-handling-improvements.md`](../../../docs/error-handling-improvements.md) §3.4, §5, §5.1 and §8. They are part of this design. This file gives the decisions.

## 1. Decisions

| ID   | Decision                                                                                                                                                                                                                                                                                   | Reason                                                                                                                                                                                                                                         |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| EF1  | One catch-all filter, `AllExceptionsFilter` with `@Catch()`, handles all exceptions. There is no second filter for `HttpException`.                                                                                                                                                        | All rules of the error response are in one place, so two filters cannot build different bodies.                                                                                                                                                |
| EF2  | `AppModule` registers the filter as the provider `APP_FILTER`, not with `app.useGlobalFilters()`. The filter gets `HttpAdapterHost`, the handlers (token `ERROR_HANDLERS`) and the logger (token `ERROR_LOGGER`) in its constructor. `AppModule` gives `backErrorHandlers` and `logError`. | The e2e tests build `AppModule` and do not run `main.ts`, so they get the filter too. A unit test gives a spy as the logger (my-thought 1 and 5, Q7).                                                                                          |
| EF3  | `packages/shared/src/api-response.ts` holds `BaseResponse`, `ErrorResponse`, `ErrorMetadata` and `ErrorDebug` (docs §3.4). They replace `ApiErrorResponse`. `message` is a text only. `metadata.errorCode` is required. There is no `exceptionName`.                                       | The back app builds the error response, and the front app reads it, so both apps use one definition. The front app reads the validation list from `details`. `BaseResponse` is also the parent of the success response (change `261126-1155`). |
| EF4  | `catch()` does the steps of docs §5 in this order: `toAppError()`, the log, the check of the context, the check of a started response, the full body, then the rules outside development, then `httpAdapter.reply()`. `toErrorResponse(appError, path)` builds the full body.              | The log comes first, so an error that gets no reply is still in the log. The filter removes the debug fields at the end (my-thought 6).                                                                                                        |
| EF5  | The debug fields `exceptionType`, `stackTrace` and `cause` are in one object, `metadata.debug`. When `isDevelopment()` is `false`, the filter deletes `metadata.debug`. For a status of 500 or more, it also sets `message` to the default message of the code.                            | One object to delete: a new debug field cannot reach production by mistake. The real message of a 5xx error can show internal details (Q3).                                                                                                    |
| EF6  | When `headersSent` is `true`, the filter sends no body (Q8). When `writableEnded` is `false`, it calls `response.destroy()`. When `writableEnded` is `true`, it does nothing more.                                                                                                         | A JSON error in an open body breaks the file, and the status stays `200`. A normal end makes a short file that looks complete. A closed connection tells the client that the download failed. NestJS 12 `StreamableFile` does the same.        |
| EF7  | The filter calls the logger in a `try`/`catch`. When the logger throws, the filter writes one line with `console.error` and continues.                                                                                                                                                     | A bug in a logger must not leave the client with no reply.                                                                                                                                                                                     |
| EF8  | `metadata.path` and the location of the `AppError` are `request.originalUrl` without the part from `?`.                                                                                                                                                                                    | A token in the query must not go to the response or to the log (earlier 4). `originalUrl` keeps the global prefix of the route.                                                                                                                |
| EF9  | The `dev` script of `apps/back/package.json` is `NODE_ENV=development nest start --watch`. `pnpm-workspace.yaml` gets `shellEmulator: true`.                                                                                                                                               | Without `NODE_ENV`, no developer sees the full body. The shell of Windows cannot read `NAME=value command`. With `shellEmulator`, pnpm runs the scripts in its own shell on each system.                                                       |
| EF10 | For a context that is not HTTP, the filter logs the `AppError` and returns. The source is `ws`, `rpc` or `graphql` for these context types, and `other` for each other type.                                                                                                               | The back app has no such context yet. The change that adds one also adds its reply (docs §11). For GraphQL, a filter that returns nothing gives `null` with no error.                                                                          |

## 2. Not in this change

| Item                                                                    | Where it goes                       |
| ----------------------------------------------------------------------- | ----------------------------------- |
| The success body `{ success: true, data, statusCode }`                  | Change `261126-1155`                |
| The reply in a WebSocket, gRPC, GraphQL or bot context                  | The change that adds the context    |
| An `error` message for SSE, and the error handler of a `StreamableFile` | The first change with SSE or a file |
| Error messages on the pages of the front app                            | A front change                      |
